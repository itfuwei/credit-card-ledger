| 项目 | 内容 |

## 1. 背景与目标

用户持有多张信用卡，卡片额度、账单日和还款日各不相同。用户需要手动记录每次资金使用，并在一个总览中快速确认各卡的额度占用、已出账金额、未出账金额和下一笔还款安排。

本产品的第一阶段目标是建立一套清晰、可复核的本地账本：录入一笔交易后，系统按照卡片账单规则自动计算其所属账期、预计出账日和预计还款日，并汇总展示。产品仅提供中性的个人账务管理能力，不提供规避银行风控、伪造交易或其他违规操作的功能。

## 2. 用户与使用场景

### 2.1 目标用户

- 持有约 10 张信用卡、需要统一管理账单和额度的个人用户。
- 希望先用浏览器本地数据完成日常记录，后续再接入登录、云端同步的用户。

### 2.2 核心使用场景

1. 用户首次打开页面，查看全部卡片的总额度、当前占用、已出账和未出账金额。
2. 用户完成一笔资金使用后，选择卡片、日期、金额、手续费和备注并保存。
3. 系统立即把该记录归入正确账期，更新卡片剩余额度及总览金额。
4. 用户查看某笔记录的预计出账日、预计还款日，或搜索某张卡、某条备注。
5. 用户发现误录时，确认后删除该笔交易。

## 4. 功能需求

### 4.1 信用卡档案

每张卡至少包含以下信息：

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| id | 卡片唯一标识 | 系统生成；未来按用户隔离 |
| bank | 发卡银行 | 必填 |
| name | 卡片名称 | 必填 |
| last4 | 卡号后四位 | 仅允许保存后四位，不保存完整卡号 |
| limitFen | 固定额度 | 非负整数，单位为分 |
| statementDay | 账单日 | 1–31；短月按最后一天处理 |
| paymentDay | 还款日 | 1–31；短月按最后一天处理 |
| color | 卡片标识色 | 可选；未填写时按发卡银行自动匹配主题色，手动颜色优先 |
| status | 卡片状态 | 至少支持 active / inactive |
| hasCheckIn | 是否需要签到 | 布尔值；仅记录提醒属性，不自动执行签到 |
| pointsRating | 积分等级 | `good` / `average` / `poor`，界面显示为优/良/差 |
| pointsRedemptionPath | 积分兑换路径 | 可选，最多 160 字符；可填写操作路径或兑换页面地址 |
| pointsProducts | 积分商城优质商品 | 数组；一张卡可维护多个值得兑换的商品 |

每个优质商品包含唯一标识、商品名称、所需积分、可选参考价值和商品说明。例如“200 积分兑换 10 元京东购物卡”或“1800 积分兑换洗衣液”。参考价值仅用于比较兑换价值，不参与信用卡账单和额度计算。

卡片状态区应显示：卡片名称、银行、后四位、总额度、已占用额度、剩余额度、额度使用率、已出账、未出账及下一还款日。

总览和信用卡档案中的每张卡均提供快捷记录交易入口；通过该入口打开交易表单时自动选择当前卡片并禁止切换信用卡。

交易表单在选择信用卡后同步展示该卡账单日和还款日；规则仍引用信用卡档案，不重复保存到交易记录。信用卡和交易流水导出文件使用中文业务名称与导出日期命名。

### 4.2 交易流水

用户新增交易时必须填写信用卡、交易日期和交易金额；手续费和备注可选。保存前需校验必填项及金额为正数，防止重复提交。交易以中性“交易/资金使用”命名。

手续费支持按交易金额的万分之 22、万分之 25、万分之 29 快捷计算；计算结果统一向上取整到分，用户仍可手动修改。

| 字段 | 说明 | 约束 |
| --- | --- | --- |
| id | 交易唯一标识 | 系统生成 |
| cardId | 所属卡片 | 必须引用现有卡片 |
| date | 交易自然日 | `YYYY-MM-DD` |
| amountFen | 交易金额 | 正整数，单位为分 |
| feeFen | 手续费 | 非负整数，单位为分；当前不计入额度占用 |
| note | 备注 | 可选，最多 80 字符 |
| createdAt | 创建时间 | ISO 8601 时间戳 |

流水列表按交易日期倒序展示；同日记录按创建时间倒序展示。列表支持按银行、卡片名称、卡号后四位和备注搜索，并显示交易金额、手续费、预计出账日、预计还款日。删除操作必须二次确认。

### 4.3 账单与额度计算

系统以本地自然日计算账单，不应受浏览器时区时间影响。金额的持久化和领域计算统一使用“分”整数，界面展示时才格式化为人民币。

| 规则 | 定义 |
| --- | --- |
| 账期归属 | 交易日不晚于当月账单日（含当天）时，归入当月账期；晚于账单日时，归入下月账期。 |
| 预计出账日 | 交易所属账期的账单日。 |
| 预计还款日 | 若还款日大于账单日，则为同月还款日；若小于或等于账单日，则为下一个自然月还款日。 |
| 短月份 | 账单日或还款日为 29–31 时，遇到短月份取该月最后一天。 |
| 已出账 | 截至“今天”，预计出账日不晚于今天的交易金额之和。 |
| 未出账 | 当前总占用减已出账金额。 |
| 当前占用 | 当前未被还款记录冲减的交易金额之和；第一阶段尚未实现还款冲减。 |
| 剩余额度 | `max(0, 固定额度 - 当前占用)`。 |
| 下一还款日 | 当前已出账且尚未到期的账期对应还款日；若已到期则切换到下一账期。 |

后续接入还款记录后，当前占用、已出账和未出账都必须按交易与还款的分配结果计算；服务端计算结果将成为最终可信结果。

### 4.4 总览与提醒

总览应在不进入详情的情况下展示以下数据：

- 卡片总数、总固定额度、总占用/欠款、总已出账、总未出账。
- 每张卡的额度使用率与剩余额度。
- 每张卡的下一还款日与距离还款日天数。
- 每张卡的活动状态，包括进行中、已达标、待领取和可领取数量。
- 每张卡头部以图标和数字紧凑显示积分等级、活动数量和优质商品数量；仅需要签到时显示“签到”标签。
- 每个活动只能处于一个状态：未达标、进行中、待领取、可领取、已过期或已领取。活动图标悬停时按状态逐行汇总数量；商品图标悬停时展示商品名称和所需积分。
- 总览卡片支持按还款日、距还款日、账单日、已用额度、可用额度、总额度和积分等级正序或倒序排序；默认按每月还款日正序排列。
- 正常、临近、紧急、逾期等状态必须同时有文字说明，不能只用颜色区分。

第一阶段仅展示计算结果；还款提醒的通知授权、定时推送和跨设备提醒属于后续需求。

## 5. 页面与交互要求

### 5.1 总览页

总览页是当前唯一页面，按以下顺序组织：

1. 应用导航与“记录交易”入口。
2. 汇总指标区。
3. 卡片状态区。
4. 最近交易表格与搜索。
5. 桌面端侧边抽屉、移动端全屏抽屉形式的交易录入。

桌面端优先保障卡片比较和表格阅读；移动端优先保障快速录入、关键还款信息与单卡信息可读。所有中文文本不得被遮挡、重叠或无提示截断；窄屏表格允许横向滚动。

### 5.2 空、错与加载状态

- 无交易时显示明确空状态和下一步提示。
- 本地数据加载时显示加载状态。
- 表单校验失败时，在对应字段附近给出中文错误提示。
- 持久化失败时提示用户操作未完成，且不能假装保存成功。

## 6. 数据、隐私与安全

- 仅管理卡片名称、银行、后四位、额度、账单日、还款日及账务记录。
- 严禁收集、展示或记录完整卡号、CVV/CVC、密码、支付密码、短信验证码和磁道信息。
- 示例数据必须是虚构数据，不能包含真实个人信息。
- 当前 localStorage 数据仅保存在当前浏览器；清理浏览器数据可能导致数据丢失，后续导出功能应降低该风险。
- 云端阶段必须具备认证、授权、用户数据隔离、HTTPS 传输、备份和可删除机制。

## 7. 非功能需求

- 使用 Vue 3、Vite、JavaScript、Composition API 和 Element Plus；不使用 React 或 TypeScript。
- 所有页面交互优先采用 Element Plus 的表单、表格、抽屉、确认框和反馈组件。
- 领域计算必须脱离 Vue 与持久化实现，放在纯函数模块中，便于测试和未来由后端复用规则。
- 数据读写必须通过 repository 边界，页面组件不能直接依赖 localStorage。
- 每次前端改动后运行 `npm run build`；涉及账单规则时补充边界测试。

## 8. 验收标准

第一阶段可视为满足需求，至少应达到以下标准：

1. 可录入并保存一笔指定卡片、日期和金额的交易，刷新页面后数据仍在。
2. 交易日期等于账单日时归入当期；账单日次日归入下期。
3. 还款日不晚于账单日时，预计还款日正确落在下一自然月；月末日期在短月正确收敛。
4. 新增或删除交易后，卡片和总览的占用、剩余额度、已出账、未出账立即同步刷新。
5. 流水可搜索、可查看预计出账/还款日期，并能在二次确认后删除。
6. 桌面与移动视口下，关键文字、按钮、表单和表格不重叠、不遮挡。
7. 不出现完整卡号、验证码、密码等敏感支付信息。
8. `npm run build` 成功通过。

## 9. 待确认事项

以下决定会影响下一阶段的数据模型和计算方式，建议在实现卡片管理、还款和后端前确认：

1. “欠款”是否等同于交易占用，还是需要支持分期、退款、溢缴款、临时额度等场景。
2. 还款是否允许一次覆盖多张卡或多期账单，以及应如何分配到具体账单。
3. 手续费是否只做记录，还是应计入应还金额、额度占用或单独统计。
4. 是否需要多币种、外币账单、分期、自动提醒与导入银行账单。
5. 云端阶段是否只支持单用户，还是从一开始设计家庭成员/共享账本。
